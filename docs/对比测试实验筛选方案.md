# 10M 参数以下 DiffusionDet 的改进与本地筛选方案

> 编写日期：2026-08-05  
> 适用目标：SAR 单类检测；模型参数量严格小于 10M；主目标 `bbox/AP >= 61`，阶段目标先超过现有 10M 以下最好结果  
> 约束：不修改、筛选、补标或针对性增强数据集；不引入只对 SAR/船舶成立的尺寸先验、形状先验或手工规则；优先采用可迁移到一般目标检测任务的结构和训练方法  
> 本文性质：研究路线与本地筛选方案，不代表尚未运行的候选已经获得所述精度
>
> 2026-08-31 状态：本方案对应的 `sar-007`～`sar-014` 筛选已经完成；最终结果、淘汰结论和 `sar-015`/`sar-016` 独立正式配置以 `docs/实验日志.md` 为准。本文保留为方案形成时的设计依据，不再作为当前进度页。

## 技术结论

目标有实现可能，但现有证据还不足以保证达到。当前唯一小于 10M 的正式结果是 `sar-003`：约 7.70M 参数、`AP=54.96`；若按实验日志的严格目标 `AP>=61`，还差 6.04 AP。另一方面，34.49M 的可信教师 `sar-006` 已达到 `AP=67.77`，说明任务本身存在足够的精度上限，关键是把模型容量从当前冗余的检测头重新分配到更有效的特征表达和定位过程。

最值得优先验证的路线不是继续一味缩小 backbone，而是以下组合：

1. 先修正并验证多步扩散推理，使已有权重能正确测试 1/2/4 步去噪、最终步输出和 ensemble；这是无需重训的低成本检查。
2. 将六个相互独立的 `RCNNHead` 改为共享或部分共享的迭代头，并保留很小的 stage-specific adapter。当前 `sar-003` 的 MobileNetV4 主干本身只有约 1.05M，而检测头约 6.47M，头部才是参数瓶颈。
3. 用共享头省下的预算，把 FPN/hidden 恢复到 96 或 128；本地构建估算表明，当前自定义 MobileNetV4-Small 配合共享 128 维头仍可约为 5.0M，而不是 34M。
4. 把当前从头训练、且与官方权重不兼容的自定义 MobileNetV4，替换为 `timm` 中具有 ImageNet 预训练权重的标准轻量 backbone。优先筛选 MobileNetV4-Conv-Small、EfficientViT-B0 和 RepViT-M0.9。
5. 使用 `sar-006` 作为冻结教师，在相同 noisy boxes、相同时间步上做查询一致的分类、框和特征蒸馏。这是最有希望补足剩余 AP 差距的方法之一，而且不增加部署模型参数。

“latent 方向”应理解为压缩和改善 proposal/token latent，而不是把输入图像再送入 VAE。DiffusionDet 的扩散状态本来就是 `N×4` 的框集合；额外图像自编码器会增加参数、训练复杂度和重建误差，并可能损害严格 IoU 下的定位细节。更合理的 latent 改进是共享迭代 proposal head、96/128 维 object latent、空间—通道可分离的 RoI 聚合，以及后期的 box flow matching。

短期本地筛选完全可行。当前 RTX 2080 Ti 已跑通 Batch 16，`sar-006` Batch 25 的峰值显存为 15,620 MB。建议用“静态构建 → 20 iter smoke → 5k/20k/50k 逐级淘汰 → 只给 1～2 个候选完整训练”的串行流程。短跑只能排除错误或明显较弱的方案，不能单独证明最终 AP；最终候选仍需完整训练和多种子复核。

## 1. 目标口径与验收标准

### 1.1 主目标

- 严格目标：可部署模型的 trainable parameters `< 10,000,000`，SAR 验证集 COCO `bbox/AP >= 61.0`。
- 用户表述的 `AP 0.6` 可理解为 60 AP；本文采用实验日志中更严格的 61 AP，以同时覆盖两种口径。
- 阶段性成功：在相同评估协议下稳定超过 `sar-003` 的 54.96，而不是要求每次结构修改一步达到 61。

### 1.2 参数量口径

建议以后同时报告两个数字：

- 主口径：`sum(p.numel() for p in model.parameters())`，即实际模型参数量。
- 审计口径：checkpoint `model` state dict 中全部 tensor 元素数；它还会包含 BN running statistics 和扩散 schedule buffers，因此略大于主口径。

筛选阶段最好把主口径控制在 9.5M 以下，为归一化、adapter、蒸馏投影层和实现差异预留至少 0.5M。蒸馏教师只在训练时存在，不计入部署学生模型参数；若训练结束仍保留教师分支，则不满足目标。

### 1.3 “不针对数据集优化”的边界

本文允许：

- 通用轻量 backbone、通用多尺度融合、共享检测头、蒸馏、通用扩散/匹配优化；
- 固定现有输入协议和训练数据，仅以目标验证集衡量模型变化；
- 使用通用 ImageNet 预训练权重；
- 用通用 corruption 测试鲁棒性。

本文不建议：

- 按本数据集船宽、长宽比、目标密度手工设计 anchor、初始框或规则后处理；
- 修改、过滤、重采样、补标或专门清洗当前数据；
- 只为当前类别增加特定纹理分支或 SAR 专用频域先验；
- 用验证集反复细调大量连续超参数而不做独立复核。

`NUM_CLASSES=1` 属于任务定义，不属于不当的数据集特化。

## 2. 现有实验能够支持什么结论

### 2.1 关键结果

| 实验 | 参数量 | AP | AP50 | AP75 | 可用于当前决策的结论 |
| --- | ---: | ---: | ---: | ---: | --- |
| `sar-006` | 34.49M | 67.77 | 96.94 | 81.20 | 固定种子、固定 256 的可信教师和精度上限参考 |
| `sar-001` | 34.49M | 66.94 | 96.83 | 80.35 | 历史方向参考；`SEED=-1` |
| `sar-002` | 17.88M | 60.96 | 95.71 | 69.41 | `STEPS>MAX_ITER`，不能作为有效的 64 维公平消融 |
| `sar-003` | 7.70M | 54.96 | 94.16 | 57.76 | 当前唯一小于 10M 的正式结果；从头训练且 `SEED=-1` |
| `sar-004` | 20.58M | 57.61 | 95.12 | 63.26 | 扩大 MobileNetV4 与 hidden 有收益，但调度有历史限制 |
| `sar-005` | 34.46M | 58.84 | 95.61 | 65.45 | 256～1024 多尺度在当前训练协议下明显退化 |

原始证据见 [实验日志](实验日志.md)、[项目交接与重启指南](项目交接与重启指南.md) 和被 Git 忽略的 `runs/sar_ship/`。

### 2.2 精度缺口主要是定位，不是粗分类

`sar-003` 的 `AP50=94.16` 已经很高，但 `AP75=57.76`，两者相差 36.40 AP；`sar-006` 的对应差距为 15.75 AP。这个现象说明小模型大多能找到目标，但边界框的精细定位明显不足。后续应优先关注：

- 保持高分辨率浅层特征的质量；
- RoI 特征聚合是否丢失空间结构；
- 多阶段框细化是否有效；
- 框回归表示和逐阶段自蒸馏；
- 教师对定位信息的传递。

因此，仅换一个参数更小的分类 backbone 不足以解决问题。

### 2.3 现有对比的证据限制

- `sar-003` 只有一次、非固定种子完整训练，不能把 54.96 当成无方差的真实均值。
- `sar-002` 的 LR 没有衰减，17.88M/60.96 不能证明“R18+64 的正常上限就是 60.96”。
- 历史 MobileNetV4 使用自定义结构并从头训练；它没有利用论文和 `timm` 中的标准 ImageNet 权重。
- 不同历史实验 Batch、迭代数、恢复次数不同，训练 step 时间不能直接当端到端速度结论。
- 当前没有独立测试集、三种子均值、端侧延迟或鲁棒性评估。

所以本文把历史结果用于确定方向和筛选门槛，不把跨实验 AP 差直接解释为单一结构因素的因果效应。

## 3. 当前模型的参数瓶颈

使用实际 checkpoint 的 `model` state dict 分组统计后，得到如下结构。

### 3.1 `sar-003`：7.70M 中检测头占 84%

| 模块 | 参数/状态 tensor 元素量 | 占比 |
| --- | ---: | ---: |
| MobileNetV4-Small bottom-up | 1.048M | 13.61% |
| FPN | 0.168M | 2.19% |
| 六级 `DynamicConv`/`inst_interact` | 4.402M | 57.16% |
| 六级 FFN `linear1+linear2` | 1.586M | 20.59% |
| 其余 attention、time、cls/reg 等 | 约 0.497M | 6.45% |

结论：继续把 1.05M 的 backbone 缩得更小，最大也只能节省约 1M；而共享或重构重达约 5.99M 的 `DynamicConv+FFN`，能同时释放数百万参数并保留增加 hidden width 的空间。

### 3.2 `sar-006`：动态头仍比 R18 主干更重

| 模块 | 参数/状态 tensor 元素量 | 占比 |
| --- | ---: | ---: |
| R18 bottom-up | 11.186M | 32.43% |
| FPN | 0.714M | 2.07% |
| 六级 `DynamicConv`/`inst_interact` | 17.503M | 50.74% |
| 六级 FFN `linear1+linear2` | 3.159M | 9.16% |
| 其余模块 | 约 1.933M | 5.60% |

这说明 34.49M 并不是“R18 本身太大”这么简单；128 维、六套不共享的 RoI 动态头才是最大单项。

### 3.3 当前头为什么重

[head.py](../diffusiondet/head.py) 中每个 `RCNNHead` 都包含一套：

- `MultiheadAttention`；
- `DynamicConv.dynamic_layer`：从 proposal feature 生成两套动态矩阵；
- `DynamicConv.out_layer`：把 `7×7×H` 的 RoI 特征一次性映射回 `H`；
- `H -> DIM_FEEDFORWARD -> H` 的 FFN；
- 分类和三层回归 MLP。

随后 `_get_clones` 完整复制 6 份。即使 `H=64`，`DIM_FEEDFORWARD` 仍固定为 2048，比例达到 32 倍；`out_layer` 的参数量随 `49H²` 增长。这两个设置在轻量模型中都不够均衡。

### 3.4 低秩并不是第一优先级

仓库已有未接入训练路径的 [low_rank.py](../diffusiondet/util/low_rank.py)。对 `sar-003` 已训练权重的四类大矩阵做 SVD 后，rank-32 平均只保留约 58%～61% 的 Frobenius 能量，rank-48 约保留 80%～82%。这表明权重并没有非常强的低秩性：

- 直接把 rank 压到 16/32 很可能明显损伤精度；
- rank-48 节省有限，而且仍需微调或蒸馏；
- 先做跨 stage 权重共享、空间—通道因子化和 FFN 缩放更合理；
- 低秩可作为后期二次压缩，而不是第一轮主线。

## 4. 代码层面的关键发现

### 4.1 当前扩散发生在框空间

[detector.py](../diffusiondet/detector.py) 中前向扩散对象是归一化后的 `(cx, cy, w, h)`，状态形状为 `batch×NUM_PROPOSALS×4`。图像只经过 backbone/FPN 形成条件特征，并没有图像生成模型意义上的 VAE latent。

因此推荐的 latent 改进是：

- proposal latent：`H=96/128` 的 object feature；
- shared recurrent latent：同一检测头反复细化框和 object feature；
- factorized RoI latent：先保留空间信息，再低成本聚合通道；
- distributional box latent：用离散分布/残差分布表示边界，而不是直接四个标量。

不推荐第一阶段加入图像 VAE、latent diffusion U-Net 或图像重建损失。

### 4.2 多步采样的最终结果没有进入 ensemble

当前 `ddim_sample` 的循环顺序是：

1. 当前时间步预测 `outputs_class/outputs_coord`；
2. 若 `time_next < 0`，执行 `continue`；
3. ensemble append 位于 `continue` 之后。

因此 `SAMPLE_STEP>1` 时，最后一个去噪步骤的预测不会被加入 ensemble。以 2 步为例，ensemble 只收集第一次 `t=999` 的输出，第二次更接近干净框的输出被丢弃。上游官方仓库当前代码也保留了相同控制流，但它与论文所述“各 sampling step 的预测经 NMS ensemble”并不完全一致，应先通过单元测试和对照评估确认预期行为，而不能直接把 `SAMPLE_STEP` 改成 2/4 后宣布多步无效。

同时，box renewal 使用 `outputs_class[-1][0]` 和形状固定为 `1×...` 的新随机框，只对 eval batch=1 安全。若以后提高测试 batch，需要逐图处理。

### 4.3 多个扩散行为被硬编码，无法可靠消融

以下值目前不是配置项：

- `timesteps=1000`；
- `objective='pred_x0'`；
- `ddim_sampling_eta=1.0`；
- `box_renewal=True`；
- `use_ensemble=True`；
- renewal threshold `0.5`；
- `self_condition=False`。

建议先配置化并保持当前值为默认，之后每次只改一个因素。`objective`、`x_self_cond` 和 `clip_x_start` 目前也没有形成完整可切换路径，不应仅改字符串。

### 4.4 当前 MobileNetV4 是本地自定义实现

[mobilenetv4.py](../diffusiondet/mobilenetv4.py) 实现了 UIB/Fused-IB 思路，但 `small` 的最后 stage 仅输出 128 通道；当前 `timm` 标准 `mobilenetv4_conv_small` 的四级 feature channels 为 `[32, 64, 96, 960]`，结构和 state dict 不兼容。历史 `sar-003` 还使用 `MODEL.WEIGHTS=""` 从头训练。

因此“给现有自定义 MobileNetV4 直接加载官方权重”不可行。正确方式是新增通用 `TimmBackbone` wrapper 或严格实现标准架构，并显式验证四级 stride、channel、FPN 名称和 checkpoint 加载率。

## 5. 优先级最高的改进方向

### 5.1 P0：先修正多步推理并做零训练评估

目的：验证扩散机制是否还能从现有权重免费获得增益，并为后续扩散消融建立可信入口。

建议修改：

- 将最终预测无条件保存为 `final_output`；
- `ENSEMBLE_MODE` 支持 `final_only`、`all_steps`、`nonfinal_steps`，默认行为先兼容旧代码；
- ensemble 明确包含或不包含最终步，并用测试固定；
- box renewal 改为 batch-safe；
- 配置化 `DDIM_ETA`、renewal threshold、box renewal 和 ensemble；
- 固定随机种子，分别评估 `SAMPLE_STEP=1/2/4`；
- 同时评估 `NUM_PROPOSALS=100/300/500`，但只作为通用速度—召回曲线，不按本数据集目标数手工选值。

可以直接使用 `sar-003/model_final.pth` 和 `sar-006/model_best.pth`，不需要训练。预期收益通常不会独自补足 6 AP，但它成本最低，而且会决定后续是否值得研究 noise schedule、flow matching 和迭代次数。

必须增加的单元测试：

- 2 步采样确实执行两次 head forward；
- `final_only` 返回最后一次预测；
- `all_steps` 的元素数等于采样步数；
- batch=2 时每张图独立 renewal，输出形状正确；
- 1 步默认输出与修改前数值一致。

> 即先用sar003.006的权重验证Difdet原先的多步推理逻辑是否有问题


### 5.2 P1：共享迭代头，把参数预算换成宽度

#### 方案 A：完全共享核心头

只实例化一个 `RCNNHead`，循环使用 6 次；用以下小模块区分 stage：

- stage embedding；
- 每 stage 独立 LayerNorm affine；
- 或 rank-4/8 residual adapter；
- 分类/回归输出层可先共享，若定位不足再改为 stage-specific。

本地实际构建估算：

| 当前自定义 backbone 上的头设置 | 参数量 |
| --- | ---: |
| 历史 `H64, 6 heads, FFN2048, Dyn64, ROI7`，不共享 | 7.67M |
| `H64, 6 iterations, FFN512, Dyn32, ROI5`，完全共享 | 1.78M |
| `H96, 6 iterations, FFN768, Dyn48, ROI5`，完全共享 | 3.00M |
| `H128, 6 iterations, FFN1024, Dyn64, ROI5`，完全共享 | 5.04M |
| `H128, 6 iterations, FFN2048, Dyn64, ROI7`，完全共享 | 5.70M |

这些数字是本地构建的 trainable parameter 计数，不是 AP 结果。

优点：

- 参数量大幅下降，但仍保留 6 次迭代计算和框细化；
- 共享函数天然适合“同一去噪器反复更新 latent”的解释；
- 可以把 hidden 恢复到与 `sar-006` 相同的 128；
- stage adapter 很小，仍有充足 10M 预算。

风险：不同 refinement stage 可能需要不同函数；完全共享可能降低表达力。应与部分共享比较。

#### 方案 B：只共享最重的模块

共享每个 stage 的：

- `inst_interact`；
- `linear1`；
- `linear2`。

保留每 stage 独立的：

- self-attention；
- normalization；
- time modulation；
- cls/reg 分支。

本地估算：当前自定义 backbone 下，`H128, FFN1024, Dyn64, ROI5` 的部分共享模型约 6.37M。它比完全共享多约 1.33M，但保留更多 stage-specific 能力，是非常值得和完全共享进行短测的折中。

#### 方案 C：四级独立头 + 更合理的中间维度

不共享权重，改用 `H96, NUM_HEADS=4, FFN512, DIM_DYNAMIC=32, ROI=5`。当前自定义 backbone 上约 5.88M。该方案保留每阶段独立参数，减少级数并提升 hidden，相比全共享风险更低，但把多个结构量同时改变，只适合先作为 prototype 筛选；正式结论需拆分因素。

#### 最先做的零训练诊断

给现有 `sar-003` 增加 stage-wise inference：分别用第 1～6 个 head 的输出评估 AP/AP75。若第 4 个 head 已接近第 6 个，减少 stage 数的风险较低；若 AP75 一直增长到第 6 个，则优先共享而不是删掉 stage。

### 5.3 P1：引入标准预训练轻量 backbone

当前环境 `timm==1.0.24` 已提供下列模型和 ImageNet 权重。通过 `features_only=True` 的本地只读构建，得到四级 feature extractor 参数量与输出：

| backbone | feature extractor | 通道 | stride | 是否有 `timm` 预训练 | 推荐级别 |
| --- | ---: | --- | --- | --- | --- |
| EfficientViT-B0 | 0.683M | 16/32/64/128 | 4/8/16/32 | 有 | 极小模型探索 |
| MobileNetV4-Conv-Small | 1.262M | 32/64/96/960 | 4/8/16/32 | 有 | 第一优先 |
| EdgeNeXt-XX-Small | 1.158M | 24/48/88/168 | 4/8/16/32 | 有 | 第二梯队 |
| FasterNet-T0 | 2.215M | 40/80/160/320 | 4/8/16/32 | 有 | 第二梯队 |
| StarNet-S1 | 2.676M | 24/48/96/192 | 4/8/16/32 | 有 | 第二梯队 |
| EfficientFormerV2-S0 | 3.246M | 32/48/96/176 | 4/8/16/32 | 有 | 第二梯队 |
| MobileOne-S0 | 4.268M | 48/128/256/1024 | 4/8/16/32 | 有 | 延迟优先备选 |
| RepViT-M0.9 | 4.718M | 48/96/192/384 | 4/8/16/32 | 有 | 精度优先备选 |

backbone 分类精度、参数量和实际检测 AP 不能直接等价，参数量也不能替代 RTX 2080 Ti/目标设备的真实延迟。第一轮只筛选三个具有互补性质的候选：

1. MobileNetV4-Conv-Small：与现有研究方向最接近，参数小、标准权重可用；
2. EfficientViT-B0：为 dense prediction 设计的轻量多尺度注意力，能补充全局上下文；
3. RepViT-M0.9：backbone 更重但表征能力更强，用共享头后仍可留在 10M 内。

以“完全共享 `H128/FFN1024/Dyn64/ROI5` 头 + vanilla FPN128”粗略估算：

| backbone | 预计总参数量 | 10M 余量 |
| --- | ---: | ---: |
| EfficientViT-B0 | 约 4.69M | 约 5.31M |
| MobileNetV4-Conv-Small | 约 5.38M | 约 4.62M |
| RepViT-M0.9 | 约 8.78M | 约 1.22M |

估算包含本地实测共享头参数、按输入通道计算的 FPN 参数和 `timm` features-only 参数；真正集成后必须重新 profile，不能把估算写成实验结果。

实现建议：新增 `diffusiondet/timm_backbone.py`，统一配置：

```yaml
MODEL:
  BACKBONE:
    NAME: "build_timm_fpn_backbone"
  TIMM:
    NAME: "mobilenetv4_conv_small.e3600_r256_in1k"
    PRETRAINED: true
    OUT_INDICES: [1, 2, 3, 4]
    OUT_FEATURES: ["stage1", "stage2", "stage3", "stage4"]
```

wrapper 必须验证实际 stride 恰为 4/8/16/32，不能只相信模型名。正式消融应先比较标准结构 scratch 与 pretrained，避免把架构和初始化收益混在一起。

### 5.4 P1：用 `sar-006` 做查询一致的检测蒸馏

`sar-006` 的 67.77 AP 比目标高 6.77 AP，适合作为固定教师。DiffusionDet 比普通 DETR 更容易构造一致的 distillation points：教师和学生可以接收同一组 `x_t` noisy boxes 和同一时间步 `t`。

推荐蒸馏结构：

1. 教师 `eval()`、`requires_grad_(False)`，只在训练时加载；
2. 数据映射只执行一次，教师和学生共享同一输入；
3. noisy boxes 和 `t` 由训练器生成一次并同时传入两者；
4. stage 0 因输入框完全一致，可直接按 query index 蒸馏；
5. 后续 stage 的框会分叉，使用教师框作为额外 distillation proposals，或对教师/学生输出做 Hungarian/IoU 对齐；
6. 总损失保留原始 GT 监督，蒸馏只作为辅助。

建议按低风险到高风险加入：

- 分类：sigmoid logits 的温度化 BCE/KL，只蒸馏教师高置信或 GT 匹配的 query；
- 框：归一化 L1 + GIoU，重点传递定位；
- object latent：用 1×1/Linear adapter 对齐 H128 教师与 H96/H128 学生；
- FPN：target-aware mask 下的特征蒸馏，不在整幅背景上做无差别 L2；
- query prior：把教师稳定匹配或教师候选作为额外训练查询。

应记录教师额外显存。若教师+学生同卡 OOM，可：

- 教师使用 `torch.no_grad()` 和 AMP；
- 把教师输出按确定性输入/augmentation 离线缓存，但这会增加存储和实现复杂度；
- 先只蒸馏最终 logits/boxes，不蒸馏全部 FPN；
- 降低训练 Batch，并按项目规则同步缩放 LR、iter、warmup 和 steps。

DETRDistill 在多种 DETR 上报告约 2.0～3.5 AP 的学生增益，KD-DETR 报告约 2.6～5.2 AP；这些跨数据集数字只能证明方向可行，不能直接加到本项目的 54.96 上。对本项目而言，“预训练 backbone + 查询一致蒸馏 + 更好的定位头”是最有机会跨过 61 的组合。

### 5.5 P2：轻量多尺度聚合，而不是堆更重的 PAN

当前 vanilla FPN 是自顶向下求和。推荐依次尝试：

#### 轻量加权 BiFPN

- 使用 1～2 个 repeat；
- 深度可分离 3×3 卷积；
- 可学习非负归一化融合权重；
- 宽度与 hidden 同为 96 或 128。

它增加的参数较少，能改善浅层定位和深层语义的双向流动。不要直接复制 EfficientDet 的深层堆叠，否则头部省下的参数会被 neck 吃掉。

#### RT-DETR 式 hybrid encoder

- 只在最低分辨率层做全局 intra-scale attention；
- 跨尺度部分用卷积融合；
- decoder 从更高质量的多尺度特征中取 RoI。

该方向对全局上下文和多尺度融合更强，但实现复杂度高于 BiFPN。第一轮不应同时更换 backbone、neck 和 head。

#### RoI 空间—通道可分离聚合

当前 `out_layer` 为 `Linear(49H, H)`，参数约为 `49H²`/stage。可改为：

1. 对每个通道做可学习 7×7 或 5×5 空间聚合；
2. 再用 `H×H` pointwise mixing；
3. 加相对坐标/位置编码，避免简单 global average 丢失框内位置。

参数约从 `49H²` 下降到 `49H + H²`，但必须以 AP75 为主要监控指标；若只看 AP50，可能掩盖定位退化。

更激进的方案是用 4～8 个 deformable sampling points 替代 49 个 RoI grid token，借鉴 Lite DETR/RT-DETRv2 的选择性多尺度采样。当前 Detectron2 `_C` 为 CPU-only，优先使用 PyTorch/TorchVision 可部署算子，避免引入当前环境无法运行的 CUDA 自定义 op。

### 5.6 P2：扩散训练本身的改进

在 P0 采样正确性建立后再做。

#### 时间步采样和损失权重

当前每图均匀采样一个 `t∈[0,999]`，直接监督 `x0` 框。可做通用消融：

- stratified timestep sampling：同一 batch 覆盖不同 log-SNR 区间，降低梯度方差；
- uniform 与 high-noise 混合采样：兼顾一步从纯噪声检测和多步细化；
- 按 clipped SNR/Min-SNR 思路给 box loss 加权；分类 loss 不应机械套用同一权重；
- 分别记录低噪声、中噪声、高噪声区间的 loss 和匹配质量。

风险：当前高 AP 的一步推理从 `t≈999` 开始，若降低高噪声训练权重，可能反而损害一步性能。任何 SNR weighting 都必须同时评估 1 步和多步。

#### 框表示与逐阶段定位自蒸馏

D-FINE 的 Fine-grained Distribution Refinement 和 GO-LSD 直接针对严格定位。可借鉴为：

- 第一阶段仍预测粗框；
- 后续 stage 对四个边界残差预测离散分布；
- 深层分布向浅层做 localization self-distillation；
- 最终部署只保留同一小头，不保留额外教师。

该方向比单纯改 `L1/GIoU` 权重更符合 `sar-003` 的 AP75 症状，但需要先做一个最小原型，只替换最后 1～2 个 stage 的回归分支。

#### 更合理的 proposal 生成

当前 concat padding 在目标较少时会用大量随机框补足 500 proposals。可研究不依赖类别/尺寸先验的通用方法：

- 训练和推理都测试 100/300/500 proposals；
- 混合随机框与 feature-conditioned top-k seeds；
- 保留一部分纯随机 proposals 维持扩散检测的泛化能力；
- 记录 recall、AP、显存和延迟，不仅记录 AP。

减少 proposals 不降低模型参数量，但会显著降低 attention/RoI 计算和蒸馏开销，并可能让短测更快。

### 5.7 P3：从 diffusion 转向 flow matching

FlowDet（2025）把框扩散改为 conditional flow matching，论文报告相对 DiffusionDet 在 COCO/LVIS 上最高约 +3.6/+4.2 AP，并强调更直的 transport path 与较少 steps；ICLR 2026 的 DiffuDETR 则把 diffusion 用于 noisy reference points/query 生成，并在不同 backbone/数据集上取得一致增益。

对本仓库可形成两个后期研究分支：

- Flow head：网络预测 box velocity，使用直线路径 `x_t=(1-t)x_0+t z`，2～4 步 ODE/flow 更新；
- Diffused query reference：只扩散参考点/框，复用更轻的共享 decoder，而不是让完整动态头承担所有生成过程。

这是潜在收益较大的研究方向，但不适合作为第一项：它会同时改变训练目标、采样器和推理路径，调试成本高，且当前 10M 基线还不可信。应在共享头、预训练 backbone 和蒸馏已经有结果后再进入。

## 6. 三个最值得做的候选架构

### 候选 1：官方 MobileNetV4-Conv-Small + shared H128 head

- backbone：`mobilenetv4_conv_small.e3600_r256_in1k`；
- FPN：先用 vanilla FPN128；
- head：6 次迭代、完全共享 `RCNNHead`，`FFN=1024`、`DIM_DYNAMIC=64`、`ROI=5`；
- stage-specific：LayerNorm affine + 小型 stage embedding；
- 预计参数：约 5.4M，加 adapter 后仍有很大余量；
- 训练：先无蒸馏，后加 `sar-006` 蒸馏。

这是第一优先，因为参数余量最大、官方预训练可用、与现有 MobileNetV4 方向最接近。

### 候选 2：RepViT-M0.9 + shared H128 head

- backbone：`repvit_m0_9.dist_450e_in1k`；
- FPN/head 同候选 1；
- 预计参数：约 8.8M；
- 优点：更多 backbone 容量可能改善表征和定位；
- 风险：余量小，实际 adapter/FPN 实现必须严格 profile；延迟不一定优于更小 CNN。

这是精度优先候选。

### 候选 3：官方 MobileNetV4-Conv-Small + 4-stage independent H96 head

- backbone：同候选 1；
- FPN/HIDDEN=96；
- `NUM_HEADS=4, FFN=512, DIM_DYNAMIC=32, ROI=5`；
- 预计参数在 6M 左右；
- 优点：保留各 refinement stage 独立参数，不承担完全共享风险；
- 风险：只有四次细化，需先看 stage-wise AP75。

这是结构风险较低的对照候选。

EfficientViT-B0 可作为极小模型备选。如果它的短测 AP 明显低于候选 1，不要仅因参数更少而继续投入；目标是 `<10M`，不是越小越好。

## 7. 适配 RTX 2080 Ti 的分阶段筛选流程

### 7.1 第 0 层：静态与单 batch 验证

每个候选必须先完成：

1. 配置解析和实验 ID 校验；
2. 模型构建、参数量和 state dict 键审计；
3. 四级 feature shape/stride/channel 检查；
4. 单 batch 前向与反向，所有 loss 有限；
5. teacher/student 同时构建时的显存探测；
6. batch=1 推理延迟、吞吐和峰值显存；
7. `git diff --check` 和相关单元测试。

静态淘汰条件：

- 参数量 `>=9.5M` 且没有明确压缩余量；
- 依赖当前机器不可用的自定义 CUDA op；
- 特征 stride 不是 4/8/16/32；
- checkpoint 预训练加载率异常；
- loss 出现 NaN/Inf；
- Batch 16 已超过约 20GB，且无合理的蒸馏/AMP解决方案。

### 7.2 第 1 层：20～200 iter smoke

- 使用下一个未占用 `sar-test-NNN`，只验证链路，不记录正式 AP 排名；
- Batch 先从 16 开始，再探测 25；
- 验证 AMP 可用性时必须单独标记数值路径；
- 保存 checkpoint 并做一次小范围推理；
- 蒸馏实验额外检查教师无梯度、显存不会持续增长。

现有 `sar-test-001` 的 20 iter 端到端墙钟为 32.63 秒，说明 smoke 成本很低。

### 7.3 第 2 层：5k/20k 早期筛选

短测训练应模拟完整训练的早期阶段，不要为了 20k pilot 把 LR milestones 强行缩到 70%/90%，否则它不再代表完整训练的前 20k。推荐两种安全方式：

- 在新正式运行中使用完整训练 schedule，按 checkpoint/eval rung 由受控 early-stop hook 正常停止，并记录 `screened_out/promoted`；
- 或建立独立 screening 类型的运行生命周期，避免把人工中断记成失败。

如果暂时不修改实验管理器，可用新的正式 ID 做 20k、无 LR decay 的 pilot；晋级后再用新 ID 从头完整训练。不要原地篡改 pilot 的冻结配置继续成长为另一实验。

所有候选使用相同：

- 固定 256 输入；
- `SEED=40244023`；
- 数据映射和损失基线；
- Batch/LR/已见样本数口径；
- 完整 `sar_ship_val`，不使用为了候选筛选而手选的验证子集。

第一轮必须包括一个“当前自定义 MobileNetV4-Small/H64 的固定种子控制组”，否则无法判断新 backbone/head 的早期曲线是否真正改善。

晋级原则不建议只设一个绝对 AP 门槛：

- 5k 用于淘汰崩溃、极慢和明显落后候选；
- 20k 保留相对控制组 AP、AP75、APs 综合最好的前 2～3 个；
- 若某候选 AP 略低但 AP75 明显更高，可保留到 50k；
- 记录每个候选的 loss 分项和 stage-wise 指标，避免只看总 loss。

### 7.4 第 3 层：50k 中期筛选

- 只保留 2～3 个候选；
- 运行完整验证集；
- 比较 AP/AP50/AP75/APs/APm/APl；
- 测 batch=1 延迟、峰值显存和参数量；
- 对多步推理测试 1/2/4 steps 的精度—延迟曲线；
- 只晋级 1～2 个完整训练。

`sar-006` 的参考曲线为：5k AP 40.95、20k AP 49.21、30k AP 52.91、60k AP 57.89、110k AP 62.58、245k 最佳 AP 67.77。不同架构收敛速度会不同，这些值只能作资源和曲线形态参考，不能成为小模型的绝对淘汰线。

### 7.5 第 4 层：完整训练与复核

完整训练候选必须：

- 使用新正式 ID，固定非负种子和有效 milestones；
- 保持与可信基线一致的固定 256 输入；
- 记录 best 与 latest；
- 首次达到目标后至少再做两个种子；
- 报告均值、标准差和最差种子，不只报告最好一次；
- 在通用 corruption 集上测试 blur、noise、brightness/contrast、JPEG 和 resize perturbation，验证改进不是只提高当前 clean val；
- 在不改模型的前提下复评 checkpoint，确认结果可重复。

#### 估算时间

按 `sar-006` 约 1.23 秒/iter 粗略估算，不含验证和启动：

| 训练量 | 基线纯迭代时间 | 用途 |
| ---: | ---: | --- |
| 20 iter | 实测约 33 秒端到端 | smoke |
| 5k | 约 1.7 小时 | 早期淘汰 |
| 20k | 约 6.8 小时 | 白天/夜间 pilot |
| 50k | 约 17.1 小时 | 中期筛选 |
| 254,264 | 约 86.9 小时；历史含验证为 3天19小时 | 完整训练 |

轻量模型可能更快，蒸馏可能更慢。应以实际前 200 iter 中位 step time 重算 ETA。

## 8. 让 Codex 持续本地探索的工程方案

当前只有一张 GPU，推荐串行 ASHA 风格队列，不要并行抢显存。

### 8.1 需要先补的工具

建议新增但不要在历史目录上写入：

- `tools/profile_model.py`：参数量、trainable 参数、MACs/FLOPs、feature shape、batch=1 latency、显存；
- `tools/evaluate_head_stages.py`：同一权重逐 stage 评估；
- `tools/screen_experiments.py`：读取候选 YAML 清单，顺序执行静态检查、smoke、rung 训练和评估；
- `tools/summarize_screening.py`：生成 CSV/Markdown 排名，保留配置 hash、Git commit、环境和失败原因；
- graceful early-stop hook：只在 checkpoint/eval 完成后停止，运行清单写 `screened_out` 或 `promoted`，不伪装成 `completed`。

### 8.2 队列状态机

```text
planned
  -> static_passed
  -> smoke_passed
  -> rung_5k
  -> rung_20k
  -> rung_50k
  -> promoted_full | screened_out | failed
  -> completed
```

每个状态保存：

- config 路径和展开后 hash；
- Git commit/dirty 状态；
- 参数量与模型结构摘要；
- PyTorch/CUDA/Detectron2/timm 版本；
- 开始、结束和 checkpoint；
- AP 分项、显存、step time、推理 latency；
- 淘汰或晋级理由。

### 8.3 Codex 执行原则

- 每次只运行一个 GPU 任务；
- 开始前检查 `nvidia-smi`、磁盘和目标目录；
- 不覆盖任何 `sar-000`～`sar-006` 产物；
- 断点恢复只使用规范 `last_checkpoint`；
- 超过 rung 后只在完整 checkpoint 已写入时停止；
- 异常时保留日志并标记失败，不自动删除重跑；
- 候选不因单次 5k 排名第一就直接全量训练；
- 只有用户明确授权后才启动数天的正式训练队列。

### 8.4 推荐的首轮探索矩阵

先做不训练的工程评估：

1. 修正 sampler；`sar-003` 与 `sar-006` 各评估 1/2/4 steps；
2. 对 `sar-003` 评估 head stage 1～6；
3. 统计 proposals 100/300/500 的 AP—延迟曲线；
4. profile 三个候选 backbone 和三种 head 结构。

再做统一 20k pilot：

| 组别 | backbone | head | 初始化 | 蒸馏 | 目的 |
| --- | --- | --- | --- | --- | --- |
| Control | 当前自定义 MNV4-S | 原 H64/6-stage | scratch | 无 | 固定种子可信短程控制 |
| H1 | 当前自定义 MNV4-S | shared H128 | scratch | 无 | 单独验证容量重分配 |
| B1 | 官方 MNV4-Conv-S | shared H128 | ImageNet | 无 | 验证标准预训练 backbone |
| B2 | EfficientViT-B0 | shared H128 | ImageNet | 无 | 极小全局多尺度候选 |
| B3 | RepViT-M0.9 | shared H128 | ImageNet | 无 | 精度优先候选 |
| D1 | B1 中的最佳设置 | shared H128 | ImageNet | `sar-006` | 验证教师能否补足定位差距 |

如果首轮实现成本要更低，可先只跑 Control、H1、B1；H1 不改善则先调整 shared/partial-shared，而不是马上集成更多 backbone。

## 9. 建议的正式单因素顺序

项目要求一次正式实验只验证一个概念因素。建议顺序如下，具体 ID 以执行时未占用编号为准：

1. 建立固定种子、固定 256、有效 schedule 的 10M 以下控制组；
2. 只把六级头改为共享，其他维度不变；
3. 在共享头基础上只把 hidden/FPN 从 64 提升到 96，再视结果提升到 128；
4. 只调整 `DIM_FEEDFORWARD` 比例；
5. 只比较完全共享与部分共享；
6. 在选定头上更换标准 backbone，先 scratch 对齐结构；
7. 同一标准 backbone 比较 scratch 与 ImageNet pretrained；
8. 在最优学生上加入蒸馏；
9. 再尝试轻量 BiFPN 或 RoI 可分离聚合；
10. 最后进入 SNR/time sampling、distributional regression 或 flow matching。

筛选 prototype 可以组合多项改动以节省时间，但一旦发现有效组合，必须回到上述顺序拆分关键因素，否则不能知道增益来自哪里。

## 10. 具体代码修改落点

### `diffusiondet/config.py`

新增并保持旧行为为默认：

- `HEAD_SHARING`: `none/full/heavy`；
- `HEAD_NUM_BANKS`；
- `STAGE_ADAPTER_DIM`；
- `ROI_AGGREGATION`: `flatten_linear/separable/deformable`；
- `TIMESTEPS`、`DDIM_ETA`、`BOX_RENEWAL`、`RENEWAL_THRESHOLD`、`ENSEMBLE_MODE`；
- `TIMESTEP_SAMPLER`、`SNR_LOSS_GAMMA`；
- `DISTILLATION.*`；
- `TIMM.*`。

### `diffusiondet/head.py`

- 用 head factory 构造独立、共享或 head bank；
- stage embedding/adapter；
- 可分离 RoI 聚合；
- 暴露逐 stage 输出和中间 object feature，供评估与蒸馏；
- 不按实验 ID 写分支。

### `diffusiondet/detector.py`

- 修复 final-step/ensemble 控制流；
- box renewal batch-safe；
- 将 noisy boxes/timestep 生成与 head forward 解耦，方便教师学生共享；
- 配置化采样行为；
- 返回可选的中间输出，默认不改变现有 API。

### `diffusiondet/loss.py`

- 可选的 timestep/SNR box loss weighting；
- 蒸馏分类、框、feature loss；
- 后期加入 distributional regression/self-distillation。

### `diffusiondet/timm_backbone.py`

- 通用 features-only adapter；
- 验证输出 stride/channel；
- 显式记录预训练权重标识和加载率；
- 兼容 FPN `ShapeSpec`。

### `tests/`

至少覆盖：

- 默认配置与旧模型结构一致；
- shared head 的参数对象确实复用，state dict 可保存/恢复；
- 不同 sharing 模式参数量符合预期；
- sampler 最终步和 batch-safe renewal；
- timm backbone 四级输出；
- teacher 不接收梯度；
- 每个新实验配置可被 `validate_experiment_configs.py` 校验。

## 11. 不建议优先投入的方向

- 图像 VAE/latent diffusion：与当前框扩散不是同一瓶颈，增加参数和定位风险。
- 直接剪掉 backbone：当前小模型 backbone 仅约 1.05M，收益上限低。
- 直接 rank-16/32 低秩替换：已训练权重能量保留不足，先做共享和因子化。
- 只做 INT8/FP16：会降低模型字节数和延迟，但不会让参数数量从 10M 以上变成 10M 以下。
- 非结构化 pruning：若部署仍保存 dense tensor，名义非零权重减少不等于参数量目标达成。
- 同时换 backbone、neck、head、loss 和 schedule 后只跑一次：即使 AP 提升也无法归因或稳定复现。
- 以 20 iter loss 或小验证子集宣布方案优胜：只能证明可运行，不能证明最终 AP。
- 继续完整训练当前历史 `sar-002` 配置：其 schedule 无效，且 17.88M 已超过目标。

## 12. 成功概率与决策建议

### 较高性价比、应立即做

1. sampler 正确性与已有权重 1/2/4-step 复评；
2. stage-wise head AP 诊断；
3. shared/partial-shared head 的参数、shape、20 iter smoke；
4. 官方 MobileNetV4-Conv-Small 预训练接入；
5. 用 `sar-006` 做同 noisy-query 蒸馏。

### 中等风险、首轮结果好时做

1. RepViT-M0.9 精度优先学生；
2. 轻量 BiFPN；
3. RoI 空间—通道可分离聚合；
4. D-FINE 式 distributional regression 与 localization self-distillation；
5. timestep stratification/SNR weighting。

### 高风险、后期研究

1. feature-conditioned proposal + random proposal 混合；
2. deformable sparse RoI sampling；
3. conditional flow matching/FlowDet 式框 transport；
4. 面向整个 backbone/head/queries 的 weight-sharing NAS。

综合判断：

- 仅调整 `SAMPLE_STEP` 或 `NUM_PROPOSALS`，大概率不足以从 54.96 到 61；
- 仅换另一个同量级 scratch backbone，也不够可靠；
- “标准预训练 backbone + H96/H128 共享迭代头 + `sar-006` 定位蒸馏”有合理机会达到或接近目标；
- 即使首次完整训练只到 57～60，只要固定种子下稳定超过 54.96，仍是有价值的阶段性进展，并可据 AP75/曲线决定下一项单因素改进。

## 14. 建议的下一步

如果开始实际实现，建议把第一轮工作限制为一个可审查的小闭环：

1. 配置化并修复 sampler，加入单元测试；
2. 用现有 `sar-003` 做 stage-wise 和 1/2/4-step 全验证集评估；
3. 实现 `HEAD_SHARING=full/heavy`，只在当前 backbone 上完成参数 profile 和 20 iter smoke；
4. 实现通用 `TimmBackbone`，只接 MobileNetV4-Conv-Small；
5. 做 Control、shared-H128、官方预训练 MNV4 三个 20k pilot；
6. 若 shared-H128 没有明显退化，再加入 `sar-006` 查询一致蒸馏；
7. 只将表现最好的 1～2 个方案推进到 50k 和完整训练。

这个顺序可以先回答三个最关键的问题：多步扩散有没有被当前控制流掩盖、检测头共享能否在不损失定位的情况下释放参数、标准预训练轻量 backbone 能否弥补 `sar-003` 的 scratch 劣势。答案明确后，再决定投入 BiFPN、D-FINE 式定位或 flow matching，能显著减少数天级无效完整训练。
